## 3. Baseline Architecture Direction

The feature extends the existing One-Point Employee Portal; it is not a standalone application.

```text
Portal UI
  -> Existing Portal Route / Controller
  -> Application Service
  -> Authorization / Policy
  -> Repository / Data Access
  -> Existing Portal / MySQL
```

No new datastore, authentication system or external integration is approved by this plan.

### Replaceable boundaries
- `RoutingPolicy`: isolates ORC routing rules that depend on BD-001..007.
- `StakeholderOutcomeService`: records the invariant action outcome; stakeholder responsibility and outcome values remain decision-gated.
- `RequestReadService`: provides requester-scoped tracking data.
- `MasterDataProvider`: reads department/location/role data after A-003 validation.

## 4. Data Model — Draft Only

Logical entities derived from the current baseline:
- `transfer_requests`
- `stakeholder_actions`
- `transfer_status_history` — **not required by the current baseline**; introduce only if BD-015/018 or implementation design requires it.

Required logical fields are defined in the slice specs. Physical schema, indexes and foreign keys are to be finalized after A-002/A-003 validation and Feature Specification Gate 1 approval.

Key integrity expectations:
- requester identity comes from the authenticated session;
- stakeholder actions are created atomically with the request;
- action outcome update is conditional on `pending = true`;
- visibility filters are enforced at the query/data-access layer;
- no PII is written to application logs.

## 5. API / Service Boundaries

Normative contracts are defined in the slice specs. Current baseline endpoints:
- `POST /api/transfer-requests` — SUB
- `GET /api/transfer-requests/{request_id}` — TRK
- `GET /api/transfer-requests` — TRK

Stakeholder-facing ACT endpoints remain **Blocked by BD-019**. The ORC slice exposes no public endpoint.

Cross-cutting conventions:
- JSON responses;
- ISO-8601 timestamps with offset;
- standard error envelope;
- 400/401/403/404/409/500 semantics as defined in `spec-slice-map.md`;
- CSRF enforcement depends on A-001 validation.

## 6. Failure / Transaction Strategy

Baseline:
1. Validate input before persistence.
2. Start one transaction for request creation and initial stakeholder-action creation.
3. Roll back the complete unit on persistence/routing failure.
4. Use idempotency protection for repeated submissions where an `Idempotency-Key` is supplied.
5. Use conditional SQL update for concurrent stakeholder outcomes.
6. Return safe error envelopes; never expose SQL, stack traces or PII.

Workflow-specific rejection/cancellation/integration failure handling remains blocked by BD-007..009 and BD-019.

## 7. Security

- Reuse existing portal authentication; no parallel auth.
- Resolve requester identity only from the authenticated session.
- Deny by default.
- Enforce visibility in the data/query layer.
- Non-visible resources use 404 to avoid existence disclosure.
- Use prepared/parameterized SQL.
- Validate all inputs server-side.
- Enforce existing portal CSRF protection once A-001 is validated.
- Do not log employee PII or free-text reason values.
